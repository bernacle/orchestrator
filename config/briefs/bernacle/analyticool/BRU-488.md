# BRU-488 operator scope: Analyticool Studio vertical slice

These decisions come from the operator. Where they conflict with the issue text, follow them.

## In scope

- **Design.** Use the approved Darkroom B+ design: `docs/design/darkroom/SPEC.md`, plus the prototype and screenshots next to it.
- **Lifecycle.** Use the existing collected-revenue proposal lifecycle from `@analyticool/core`: `generateMetricProposal`, `resolveMetricClarification`, `submitMetricProposal`, `approveMetricProposal`, `rejectMetricProposal`, `publishMetricProposal` and `reviseMetricVersion`. Do not add lifecycle states or change core contracts.
- **Flow.** The Studio walks through Describe → Clarify → Review → Embed.
- **Numbers.** Every figure comes from real `@analyticool/core` calculations on the existing synthetic fixtures (for example `calculateMonthlyRevenue` via the demo's `getDemoMetric`). Hard-coded numbers are not allowed.
- **Embedding.** Use the existing result-prop React SDK from `@analyticool/react`: `<MetricChart result={…} />` and `<MetricKpi result={…} />`. Do not change the public API of `packages/react`.
- **Approval.** Approval stays local: no authentication, no persistence. The UI states that plainly.
- **Truthful labels.** Results are synthetic. Label fixture data, draft previews and local approval as what they are.

## Out of scope

- A hosted analytics platform: no backend, accounts, persistence, tenancy, connectors, hosted embeds or API tokens.
- BRU-463's broader net-receipts work, beyond using what is already on `main`.
- BRU-485's customisable external SDK.
- New dependencies (the implementer cannot install packages), and network access at build time (for example fetching web fonts).

## Constraints that follow from the scope

- Do not present a hosted `<Metric id … token … />` snippet as something a developer can copy and use. If the design shows it, label it clearly as not available, or leave it out.
- Keep the change inside `apps/demo` (plus tests). Touch `packages/core` or `packages/react` only if a test proves it necessary, and explain why in the summary.

## Still open (implementer: choose conservatively and list the choice under "Decisions for review")

- The display font default, within the constraints above: no new packages, no build-time network.
- Whether approval offers a timed Undo. Core has no un-approve transition, so Undo would be a UI-only delay before approving.
- Whether Describe accepts free text or offers the supported example prompts as its primary input.
